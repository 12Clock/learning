# Prompt 技术

> 涵盖：Few-shot、Chain-of-Thought、System Prompt 约束、JSON 输出稳定性、追问策略、多语言、示例数量。

## Q: 如何用 Few-shot Prompt 让 LLM 做意图分类？

### 完整示例

```markdown
## System Prompt
你是一个意图分类器。将用户输入分类到以下意图之一：
- `weather_query`: 查询天气
- `book_flight`: 预订机票
- `chitchat`: 闲聊
- `unknown`: 无法归入以上类别
仅输出 JSON，不要解释。

## Few-shot 示例
用户: 明天北京会下雨吗
输出: {"intent": "weather_query", "confidence": 0.95}

用户: 帮我订一张去上海的机票
输出: {"intent": "book_flight", "confidence": 0.98}

用户: 你好呀
输出: {"intent": "chitchat", "confidence": 0.92}

用户: 量子计算的原理是什么
输出: {"intent": "unknown", "confidence": 0.88}

## 当前输入
用户: {user_query}
输出:
```

### 设计要点

1. **示例数量**：每个意图 1-3 个，总共不超过 10-15 个。太多浪费 token 且收益递减。
2. **覆盖典型 + 边界**：包含容易混淆的意图各给一个对比示例；包含 `unknown` 示例。
3. **示例顺序**：将与当前查询最可能相关的示例放最后——LLM 对末尾内容注意力更高（recency bias）。
4. **动态 Few-shot**：用 embedding 相似度从大例子池中动态选择与当前 query 最相似的 K 个示例，比固定示例更精准。

## Q: Chain-of-Thought 对复杂意图识别有帮助吗？为什么？

### 结论：有帮助，但仅限于复杂/模糊意图

**有效场景**：

1. **复合意图拆分**：
```
用户: "查一下天气，顺便帮我订张机票"
不用 CoT: {"intent": "book_flight"}  ← 只识别了一个
用 CoT: 思考→用户提了两个请求→ {"intents": ["weather_query", "book_flight"]}
```

2. **需要推理的隐含意图**：
```
用户: "我后天要去上海出差，但还没准备好"
不用 CoT: {"intent": "chitchat"}  ← 误判
用 CoT: "后天出差"暗示出行需求，"没准备好"暗示需要帮助→ {"intent": "travel_planning"}
```

3. **消歧**：CoT 过程中模型会引入上下文和常识推理来消除歧义。

### 为什么有帮助

1. **强制分解问题**：先分析要素再判断，减少跳跃式错误
2. **隐式上下文利用**：推理过程自然引入对话历史和常识
3. **可解释性**：推理过程就是"为什么这么分类"的解释

### 何时不用

- 意图明确的简单查询（CoT 浪费）
- 极端延迟敏感（CoT 增加 100-300ms）
- 意图数量少且边界清晰（Few-shot 直接分类已 >98%）

**实践**：默认不用 CoT；置信度低时再带 CoT 重试。

## Q: 如何设计 System Prompt 来约束 Agent 的意图识别范围？

### 模板结构

```markdown
你是 [产品名] 的意图分类模块。你的唯一职责是将用户输入分类到以下意图之一。

## 支持的意图
| 意图标签 | 含义 | 典型表达 |
|---|---|---|
| `order_query` | 查询订单状态 | "我的快递到哪了" |
| `refund_request` | 申请退款 | "我要退货" |
| `out_of_scope` | 不属于以上任何类别 | "今天天气怎么样" |

## 输出规则
1. 必须且只能输出上述意图之一
2. 不要回答用户的问题，只做分类
3. 输出格式：`{"intent": "xxx", "confidence": 0.xx}`
```

### 关键技巧

1. **封闭式意图列表**：显式列出所有合法意图 + 兜底类。不用"等"、"类似"这种开放式表述。
2. **正面约束 > 负面约束**："你的唯一输出是 JSON" 优于 "不要回答问题"。
3. **边界 case 显式处理**：多意图时的优先级、模糊时的默认行为。
4. **角色隔离**："你不是助手，不是客服。你是一个分类函数。输入：文本。输出：JSON。"

## Q: 用户意图模糊（如"帮我弄一下"）时，Prompt 中如何设计追问策略？

模糊意图的核心特征：**动词宽泛 + 缺少关键实体**。

### 追问策略层次

**Level 1：选项式追问（优先）**
```
用户: "帮我弄一下"
Agent: "你是想：A. 查询订单  B. 修改信息  C. 其他？"
```

**Level 2：引导式追问（次选）**
```
用户: "帮我处理一下那个问题"
Agent: "你说的是哪个问题？能具体描述一下吗？"
```

**Level 3：确认式追问（有把握时）**
```
用户: "弄一下上次说的"
Agent: "你是说上次提到的退款申请吗？"（基于对话历史推断）
```

### Prompt 实现

```markdown
## 模糊意图处理
当用户输入无法明确分类时：
1. 不要猜测意图
2. 提供 2-3 个最可能的选项供选择
3. 输出: {"intent": "need_clarification", "clarification": {"question": "...", "options": [...]}}
```

**关键原则**：最多追问 2 次；追问要带上上次的回答；始终包含"其他"选项。

## Q: 意图识别结果以 JSON 输出时，Prompt 怎么写更稳定？

### 五个关键技巧

**1. 提供 JSON Schema**：显式定义字段名、类型、取值范围。

**2. Few-shot 格式完全一致**：所有示例的字段顺序、嵌套、引号风格必须统一。

**3. 强约束尾部**："严格输出 JSON，不要输出任何解释。输出以 `{` 开头，以 `}` 结尾。"

**4. Function Calling（最稳定）**：将意图识别定义为 tool，由模型结构化生成机制保证格式正确。

**5. 防御性解析**：代码层用正则提取 JSON 块 + try/except 兜底。

**稳定性排序**：Function Calling > JSON Schema + 统一示例 > 纯文字 Prompt 约束

## Q: 如何通过 Prompt 让模型在不确定意图时主动反问，而不是瞎猜？

### 核心问题

LLM 的默认行为是**尽力回答**——即使不确定也会给出一个"看起来合理"的答案。要让模型"不确定就问"，需要显式打破这个默认行为。

### Prompt 设计

```markdown
## 确定性规则

你的分类必须基于充足的证据。遵循以下规则：

1. 如果你对分类结果的把握 ≥ 80%，直接输出分类结果
2. 如果把握 < 80%，输出 need_clarification 并生成一个澄清问题
3. 绝对不要在不确定时硬猜一个意图

判断"不确定"的信号：
- 用户的动词/名词可以映射到 2 个以上的意图
- 缺少关键实体（如"帮我查一下"——查什么？）
- 用户使用了代词但上下文不足以消解
```

### 关键设计原则

**1. 给"不确定"一个合法出口**

如果 Prompt 中只列了业务意图而没有 `need_clarification`，模型被迫在已有选项中选一个——这就是"瞎猜"的根源。必须让"不确定"成为一个合法的、被鼓励的输出选项。

**2. 定义"不确定"的具体标准**

不要说"如果不确定就追问"（太模糊），而是列出具体判断条件：
- 缺少必填实体 → 追问
- 两个意图的可能性接近 → 追问
- 用户表述极短（<5 个字）且含义模糊 → 追问

**3. 提供追问的示例**

```
用户: "帮我看看"
输出: {"intent": "need_clarification", "question": "你想让我帮你看什么？是查询订单、检查物流还是其他？"}

用户: "处理一下"
输出: {"intent": "need_clarification", "question": "你想处理哪个方面？退款、换货还是其他？"}
```

如果不给追问示例，模型知道可以追问但不知道追问的格式和风格。

**4. 惩罚猜错 > 奖励猜对**

在 Prompt 中强调"猜错的后果比追问一次的成本高得多"：

```markdown
重要：错误分类会导致用户被路由到错误的处理流程，浪费用户时间。
宁可多问一句，也不要猜错意图。
```

## Q: 多语言场景下，意图识别的 Prompt 设计有什么不同？

### 核心挑战

1. **同一意图的不同语言表达差异巨大**：中文"帮我退一下" vs 英文 "I'd like a refund" vs 日文 "返品したいのですが"——语法结构、礼貌程度、表达习惯完全不同。
2. **语码混杂（Code-switching）**：用户混合使用多种语言（"帮我 cancel 这个 order"）。
3. **文化差异导致意图表达方式不同**：日本用户倾向间接表达（"可能有点不太方便..."实际意思是"我不满意"）。

### 设计策略

**策略一：语言检测前置 + 语言特定 Prompt**

```python
language = detect_language(user_input)
prompt = load_prompt(f"intent_classifier_{language}.md")
result = llm(prompt, user_input)
```

每种语言一套 Prompt 和 Few-shot 示例。优点：示例与用户语言匹配，精度最高。缺点：维护成本翻倍。

**策略二：统一 Prompt + 多语言示例**

```markdown
## 示例（多语言覆盖）
用户: 明天天气怎么样
输出: {"intent": "weather", "language": "zh"}

用户: What's the weather tomorrow?
输出: {"intent": "weather", "language": "en"}

用户: 明日の天気は？
输出: {"intent": "weather", "language": "ja"}
```

一套 Prompt 覆盖所有语言，每个意图给出多语言示例。适合支持 3-5 种语言的场景。

**策略三：翻译后统一处理**

```
用户输入(任意语言) → 翻译为英文 → 英文意图识别 → 结果
```

只维护一套英文 Prompt。缺点：翻译引入延迟和误差；某些文化特定表达翻译后丢失语义。

### 实践建议

- 主要语言（如中/英）用策略二（多语言示例），保证精度
- 长尾语言用策略三（翻译后处理），降低维护成本
- Prompt 中的指令语言用英文（大部分 LLM 对英文指令的遵循度最高），Few-shot 示例用目标语言

## Q: Few-shot 示例在意图识别 Prompt 中放几个效果最好？

### 经验数据

| 示例数量 | 效果 | 说明 |
|---|---|---|
| **0（Zero-shot）** | 基线 | 只靠意图描述，简单意图可用，复杂/模糊场景差 |
| **1-2 / 意图** | 显著提升 | 最大边际收益在这里，从 0→1 的提升最明显 |
| **3-5 / 意图** | 稳定提升 | 覆盖了典型和边界表达，性价比最优 |
| **5-10 / 意图** | 收益递减 | 提升很小，但 token 成本翻倍 |
| **10+ / 意图** | 可能退化 | 过多示例可能导致模型过度拟合示例模式，泛化性下降 |

### 推荐策略

**一般场景（5-10 个意图）**：每个意图 **2-3 个**示例，总共 10-30 个。

**示例质量 > 数量**。3 个精选示例好于 10 个随机示例。选择标准：
1. **典型表达**（高频、标准说法）：1 个
2. **变体表达**（非标准但常见的说法）：1 个
3. **边界 case**（容易与其他意图混淆的表达）：1 个

```
# 意图: refund_request
典型: "我要退款"
变体: "这个东西不想要了，能退钱不"
边界: "这个质量有问题"  ← 可能被误判为 complaint
```

**动态调整**：线上监控各意图的准确率，对准确率低的意图追加示例；对准确率已经很高的意图减少示例以节省 token。

### Token 成本估算

假设每个示例 ~30 tokens（输入 + 输出）：
- 5 个意图 × 3 个示例 = 15 个示例 × 30 tokens = **450 tokens**
- 10 个意图 × 3 个示例 = 30 个示例 × 30 tokens = **900 tokens**
- 20 个意图 × 3 个示例 = 60 个示例 × 30 tokens = **1800 tokens**

当意图数量 >15 时，Few-shot 的 token 成本开始显著，应考虑动态 Few-shot（只选最相关的 K 个示例）。
